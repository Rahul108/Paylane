# Paylane: Project Prompt and Plan

Master prompt for an agentic coding tool. Paylane (each payment journey runs in its own lane) is a local-only payment platform built as independent microservices in Go, with mock payment gateways, a JWE-secured service mesh and a test console.

## 1. Mission

Build Paylane, a payment platform that models how a real payment system works end to end, without any real money or real payment gateway (PGW). It must support:

- Payment through MFS (mobile wallet, bKash-like) and cards, with and without a UI Everything runs locally with one command. No real credentials, no real PGW integration.

* redirect journey.
* Journeys that combine payment with downstream actions: payment + recharge, payment + cashback, payment + offer subscription.
* Binding and unbinding of MFS wallets and cards, and UI-less payment using a bound token.
* Mock PGWs (separate for MFS and card) that behave like real ones: hosted pages, OTP, callbacks, failures, delays, duplicate callbacks.
* A frontend with a test console to exercise every scenario locally.
* All service-to-service communication secured with JWE.

## 2. Non-negotiable rules

1. **Real microservices, no monorepo.** Every service is its own repository with its own `go.mod`, Dockerfile, migrations, tests and README. No `go.work`, no shared source tree, no cross-service imports. Services talk only over the network.
2. **Database per service.** Each service owns its MySQL database and DB user. No service reads or writes another service's tables.
3. **No shared domain code.** Each service defines its own request/response structs. The contract is the HTTP API (documented with OpenAPI in the docs). The only shared code is the infrastructure library `paylane-jwe`, its own versioned module consumed through a git tag.
4. **Money is `int64` in minor units** (poisha) plus a currency code. Never float.
5. **IDs are ULIDs generated by the application**, not by the database.
6. **Only payment-core decides payment truth.** Orchestrator and web only ask payment-core and react.
7. **The orchestrator contains no payment rules.** It knows only which step follows which, and records progress.
8. **Fail loudly.** Illegal state transitions, bad signatures, unknown keys, expired tokens and unknown routes are rejected with explicit errors, never silently ignored.
9. **Never log or store** full card numbers, CVV, OTPs, private keys or raw JWE tokens.
10. **Documentation is part of the code.** Every change that alters behaviour updates `docs/` in the same change (see section 13).

## 3. Repositories and layout

The root directory is the `paylane-platform` repository. It holds the shared docs, `agents.md`, local environment tooling and nothing else. Each service lives in `services/<name>` as its own independent git repository (git-ignored by the platform repo, created by `scripts/bootstrap.sh`).


## 5. Architecture

```
Browser
  ↓ session cookie
web (Next.js server side = BFF)
  ↓ JWE
orchestrator ──JWE──→ mock-downstream (recharge, cashback, subscription)
  ↓ JWE
payment-core ──JWE──→ mock-mfs
      ↑               → mock-card
      └── JWE callbacks from the mock PGWs
```

The mock PGWs are treated exactly like external providers: payment-core reaches them only through adapters, and they reach payment-core only through signed webhooks.

### Main flow: payment with UI

1. Browser asks web to start a journey (for example `payment_recharge`, method `mfs`).
2. Web (BFF) calls orchestrator over JWE. Orchestrator creates a journey row and calls payment-core to create a payment with an idempotency key.
3. Payment-core creates the payment (`CREATED`), calls the provider adapter, gets a hosted-page URL, moves to `PENDING`, returns the URL.
4. Orchestrator returns the URL to web, web redirects the browser to the mock PGW page.
5. User completes (or fails, or abandons) the payment on the mock page.
6. Mock PGW sends a server-to-server webhook to payment-core and redirects the browser to the return URL on web.
7. Payment-core verifies, runs the state transition, writes the ledger entry and an outbox event.
8. Outbox publisher delivers the event to orchestrator over JWE. Orchestrator advances the journey and calls the downstream API (recharge, cashback, subscription) with an idempotency key, recording each attempt.
9. Web shows the result by asking orchestrator for journey status. The browser redirect parameters are never trusted.

### Main flow: UI-less payment

A bound token is passed to payment-core, which charges the provider directly through the adapter without any browser redirect. The rest (webhook or synchronous result, ledger, event, downstream steps) is identical.

## 6. Tech stack

| Area | Choice |
| --- | --- |
| Language | Go 1.22 or newer |
| HTTP | standard library `net/http` with `ServeMux` (method and `{param}` patterns). No Gin, no Fiber |
| Database | MySQL 8.0 (InnoDB), `database/sql` with `go-sql-driver/mysql` |
| Queries | `sqlc` |
| Migrations | `goose`, one small migration per change |
| JWE and JWS | `go-jose/v4` |
| Logging | `log/slog`, JSON output, request IDs |
| IDs | ULID |
| Mock PGW pages | `html/template`, served by the mock itself |
| Frontend | Next.js (TypeScript), `jose` for JWE on the server side |
| Local run | Docker Compose |

MySQL notes the agent must follow: connection string includes `parseTime=true&loc=UTC&charset=utf8mb4`; lock rows by primary key (`SELECT ... WHERE id = ? FOR UPDATE`) to avoid gap-lock deadlocks; no `RETURNING`, so IDs are generated in the app; no partial indexes, so use composite indexes such as `(status, updated_at)`; outbox workers use `FOR UPDATE SKIP LOCKED`; keep each migration small because DDL is not transactional.

## 7. Service-to-service security (JWE)

Every internal request and response body is a nested token: **sign first (JWS), then encrypt (JWE)**.

```
send:    payload → sign with sender private key → encrypt with receiver public key
receive: decrypt with own private key → verify with sender public key → use
```

- Encryption: `RSA-OAEP-256` key wrapping with `A256GCM` content encryption. Signing: `RS256` or `ES256`. Use separate key pairs for signing and encryption.
- Every service has its own key pair. Public keys are distributed through a local key registry (files in `keys/`, generated by `scripts/keygen`, mounted read-only into containers).
- Required claims: `iss` (sender), `aud` (receiver), `iat`, `exp` (short, about 60 seconds), `jti` (unique id). Receivers reject wrong `aud`, expired tokens, unknown `iss`, and replayed `jti` (small in-memory or DB cache within the expiry window).
- Business headers like `Idempotency-Key` travel outside the token but are repeated inside the signed payload and must match.
- The browser never holds service keys. Browser to web uses a normal session cookie; web's server side performs JWE toward the orchestrator.
- `paylane-jwe` exposes: `Seal(payload, senderKey, receiverPublicKey)`, `Open(token, receiverKey, resolveSender)`, and an `http.Handler` middleware plus a client helper. It has its own tests including tampering, wrong audience, expiry and replay.
- Every service ships a test proving that a call without a valid token is rejected with `401`.

## 8. payment-core

### State machine

```
CREATED → PENDING → AUTHORIZED → CAPTURED → REFUNDED
             ↓          ↓
          FAILED     EXPIRED          (FAILED, EXPIRED, REFUNDED are terminal)
```

`PENDING → CAPTURED` is also allowed for providers that authorize and capture in one step. All state changes go through a single `Transition(paymentID, to, reason)` function that, inside one DB transaction: locks the row by primary key, returns quietly if already in the target state (idempotent), rejects illegal transitions, updates status, writes ledger entries, appends an outbox event and a row in `payment_events`. Webhooks, timeout jobs and reconciliation all use this one function. A late success for an `EXPIRED` payment is not applied; it is recorded as a reconciliation mismatch.

### Responsibilities

- **Initiation:** validate request, enforce the unique `idempotency_key`, create payment, pick adapter by method, create provider session. A duplicate key returns the original payment.
- **Provider adapters:** one interface (`CreateSession`, `Charge` for bound tokens, `Verify`, `Refund`, `Bind`, `Unbind`). Implementations: `mfs` and `card`, both talking to the mock PGWs. Adapters hide provider differences; the core never branches on provider names outside the registry.
- **Webhook intake:** `POST /webhooks/{provider}`, verify JWE signature, map the provider event to a transition, store the raw event (deduplicated by provider event id).
- **Retrieval:** `GET /payments/{id}` and list/filter endpoints.
- **Ledger:** immutable double-entry rows (debit/credit, amount, payment id, reason). Corrections are new reversing entries, never updates.
- **Refunds:** full and partial, only from `CAPTURED`, tracked as their own records, ledger reversed accordingly.
- **Timeouts:** a worker finds payments stuck in `PENDING` or `AUTHORIZED` past a limit, asks the provider via `Verify`, then transitions or expires them.
- **Reconciliation:** a job fetches the provider's settlement report from the mock PGW and compares it with payments and ledger. It records mismatches (provider says success, core says pending, amount differences, missing records) in `reconciliation_items` and exposes them through an API.
- **Outbox:** events (`payment.captured`, `payment.failed`, `payment.expired`, `payment.refunded`, `binding.created`, `binding.removed`) are written in the same transaction as the state change and delivered to subscribers (orchestrator) over JWE with retry and backoff. Consumers deduplicate by event id.

### Bind and unbind

- **Card:** card details are entered only on the mock-card hosted page. The mock returns a token, brand and last four digits. Payment-core stores token reference, brand, last4, expiry month/year and status. It never sees the full number or CVV.
- **MFS:** the user binds a wallet number on the mock-mfs page with OTP. The mock returns an agreement id. Payment-core stores the agreement id, masked wallet number and status.
- **Unbind:** payment-core calls the provider to revoke, then marks the binding `UNBOUND` (soft state, history kept).
- Bindings belong to a customer id and are used by UI-less payment. Charging an unbound or foreign token is rejected.

### Main tables (illustrative)

`payments`, `payment_events`, `ledger_entries`, `refunds`, `bindings`, `webhook_events`, `outbox`, `reconciliation_items`, `provider_sessions`.

## 9. orchestrator

The orchestrator runs journeys defined in configuration, not hardcoded flows.

| Journey | Steps |
| --- | --- |
| `ui_payment` | PAYMENT (redirect) |
| `uiless_payment` | PAYMENT (bound token, no redirect) |
| `payment_recharge` | PAYMENT → RECHARGE |
| `payment_cashback` | PAYMENT → CASHBACK |
| `payment_subscription` | PAYMENT → SUBSCRIBE |

- Tables: `journeys` (id, type, customer, status, input, timestamps) and `journey_steps` (journey id, step name, status, attempt count, last error, request/response summary, downstream reference, timestamps).
- Step statuses: `PENDING`, `RUNNING`, `SUCCEEDED`, `FAILED`, `RETRYING`, `NEEDS_ATTENTION`. Journey statuses: `STARTED`, `AWAITING_PAYMENT`, `RUNNING_STEPS`, `COMPLETED`, `FAILED`, `NEEDS_ATTENTION`.
- The PAYMENT step completes only when payment-core says so (event or status query). A periodic sweep re-queries payment-core for journeys waiting too long, so a lost event does not strand a journey.
- Downstream calls use an idempotency key built from `journeyId + stepName`, retry with backoff, and after the limit mark the step `NEEDS_ATTENTION`. Money was taken but the service was not delivered: this must be visible in the console. No automatic refund in v1; the console offers a manual refund request that calls payment-core.
- The orchestrator never inspects provider details and never changes payment state.

## 10. Mock PGWs and downstream

Mock PGWs and mock-downstream are real standalone services with their own DB (for sessions, bindings and call logs) and are never imported by other code.

### mock-mfs

Hosted pages: pay (wallet number, PIN, OTP), bind, unbind. Server API: create session, query status, charge by agreement, revoke agreement, settlement report. Sends signed webhooks to payment-core and redirects the browser to the return URL.

### mock-card

Hosted pages: card entry for pay and for tokenize/bind, then a 3DS-style OTP step. Test card numbers decide the outcome (for example one succeeds, one declines for insufficient funds, one requires OTP, one times out). Server API: create session, query status, charge by token, delete token, settlement report, refund.

### Scenario control (both PGWs)

A control API and UI let the test console choose behaviour per session or globally: success; fail (insufficient balance, wrong PIN/OTP, declined); user abandons (no callback); delayed callback (N seconds); duplicate callback (sent twice or three times); callback before redirect or after; callback with bad signature; slow or timing-out API; provider says success but core never hears (reconciliation case).

### mock-downstream

Endpoints for recharge, cashback grant and subscription activation. Each honours idempotency keys and has scenario control: success, fail, timeout, fail-then-succeed (retry testing), duplicate request detection.

## 11. Frontend (web)

Next.js in TypeScript. Its server side is the BFF: it keeps the user session, and signs and encrypts every call to the orchestrator.

- **Customer screens:** choose journey and method, pay (redirect), pay with a saved method (UI-less), manage saved MFS wallets and cards (bind, unbind), result and history pages.
- **Return pages** that show status by querying the orchestrator, never from URL parameters.
- **Test console** (a separate section of the same app):
  - start any journey with any method;
  - choose PGW and downstream scenarios before running;
  - live views: payment state and transition history, journey and step status with attempts, ledger entries, outbox events, webhook log, reconciliation mismatches;
  - actions: trigger timeout sweep, run reconciliation, retry a step, request refund, replay a webhook, send a duplicate callback.

## 12. Data and ID conventions

- Tables use `CHAR(26)` ULID primary keys, `BIGINT` amounts, `CHAR(3)` currency, `DATETIME(6)` in UTC.
- Payment idempotency key is `UNIQUE`; a duplicate insert (MySQL error 1062) returns the original payment.
- All timestamps are UTC. All status columns use the exact enum strings above.

## 14. Testing

- Unit tests for the state machine (every legal and illegal transition), money handling, JWE library and journey definitions.
- Integration tests per service against a real MySQL container.
- Concurrency tests: two simultaneous callbacks for one payment produce exactly one ledger entry.
- Idempotency tests: duplicate create, duplicate webhook, duplicate downstream call.
- Security tests: missing, expired, wrongly addressed, replayed and tampered tokens are rejected.
- End-to-end script (`scripts/e2e`) that runs the whole stack and covers: success, failure, abandon, delayed and duplicate callback, downstream failure with retry, UI-less payment, bind then unbind, reconciliation mismatch.

## 15. Delivery phases

Each phase ends with working code, passing tests and updated docs. Stop and summarise after each phase before starting the next.

1. **Foundation:** platform repo, `agents.md`, docs skeleton, docker compose with MySQL and per-service databases, keygen, `paylane-jwe` with tests, empty service skeletons that start and answer a signed health call.
2. **payment-core:** schema, state machine, idempotency, ledger, adapter interface, webhook intake, outbox, retrieval API.
3. **mock-mfs and mock-card:** hosted pages, scenarios, callbacks, settlement reports, adapters wired into payment-core, first end-to-end payment.
4. **Bind and unbind**, plus UI-less payment.
5. **orchestrator and mock-downstream:** journeys, step tracking, retries, `NEEDS_ATTENTION`, event consumption and sweep.
6. **Timeouts, refunds and reconciliation.**
7. **web:** customer flows and the full test console.
8. **Hardening:** e2e suite, docs review, runbooks, ADRs.

## 16. Definition of done

- `docker compose up` starts everything; `scripts/e2e` passes.
- Every scenario in section 10 can be triggered from the test console.
- No service imports another service's code; no `go.work` exists.
- Every inter-service call is JWE protected and has a rejection test.
- `agents.md` lookup table and all module docs match the code.

## 17. Assumptions to confirm

- Authentication of end customers is a simple local login or fixed demo users; real identity management is out of scope.
- A single currency (BDT) is enough for v1.
- Events go over direct JWE HTTP delivery from the outbox; a message broker can be introduced later behind the same outbox interface.
- Settlement files from the mock PGWs are generated on demand, not on a real schedule.
